# AIOps Automated Incident Response — Engineering Report

## Lab Work 5

---

## 1. Overview

This report documents the design and implementation of the **AIOps Automated Incident Response Engine** for Lab Work 5. The engine completes the AIOps pipeline by consuming incident records generated by the Lab 2 detection engine and automatically executing remediation actions based on configurable response policies.

The system is implemented as a Laravel Artisan command:

```
php artisan aiops:respond
```

It can run as a continuous daemon (`--once` flag for single-cycle mode) and supports `--dry-run` for testing without persisting response logs.

## 2. Architecture

```

  (from Lab 2 Detection Engine)       (Response Policies)
          │                                  │
          ▼                                  ▼
  ┌───────────────────────────────────────────────┐
  │         RunAIOpsResponse Command              │

  │  1. Load OPEN incidents                       │

                      │
                      ▼
          storage/aiops/responses.json
```

## 3. Response Policies

Policies are defined in `config/aiops.php` and map each incident type to a set of ordered actions:

| Incident Type              | Actions                                        | Escalation     | Cooldown |
| -------------------------- | ---------------------------------------------- | -------------- | -------- |
| `LATENCY_SPIKE`            | restart_service, flush_cache                   | CRITICAL_ALERT | 120s     |
| `ERROR_STORM`              | send_alert, throttle_traffic                   | CRITICAL_ALERT | 60s      |
| `TRAFFIC_SURGE`            | scale_service, enable_queue                    | CRITICAL_ALERT | 180s     |
| `SERVICE_DEGRADATION`      | send_alert, restart_service, throttle_traffic  | CRITICAL_ALERT | 60s      |
| `LOCALIZED_ENDPOINT_FAILURE` | send_alert, enable_circuit_breaker           | CRITICAL_ALERT | 120s     |

Each policy also defines `max_retries` — the number of failed attempts before the engine triggers escalation.

---

## 4. Action Execution

All actions are **simulated** with realistic logging. Each action type models a specific infrastructure operation:

| Action Type             | Simulation Behavior                                           |
| ----------------------- | ------------------------------------------------------------- |
| `restart_service`       | Simulates PHP-FPM restart with PID recycling (100ms delay)    |
| `send_alert`            | Simulates dispatch to ops-team channel (50ms delay)           |
| `throttle_traffic`      | Simulates enabling rate limiting on endpoints (80ms delay)    |
| `scale_service`         | Simulates horizontal scaling from 2→6 instances (200ms delay) |
| `flush_cache`           | Simulates app/route/config cache clear (30ms delay)           |
| `enable_queue`          | Simulates request queue activation (60ms delay)               |
| `enable_circuit_breaker`| Simulates circuit breaker trip for fast-fail (40ms delay)     |

Each action returns a structured result with `success`, `message`, and `duration_ms`.

```json
    "result": "success",
    "notes": "Alert dispatched to 'ops-team' channel. Affected: /api/normal, /api/slow, /api/db, /api/error, /api/validate. Severity: critical."
}
```

## 6. Escalation Logic

The engine implements a retry-based escalation strategy:

1. Each incident type has a `max_retries` threshold (default: 2-3).
2. If an action **fails**, the retry counter increments.
3. Once `retries >= max_retries`, the engine triggers **CRITICAL_ALERT** escalation.
4. Escalation notifies `ops-manager`, `sre-lead`, and `platform-oncall` via `pagerduty`.
5. The escalation itself is logged as a response with `result: "escalated"`.

This ensures that persistent anomalies are always surfaced to human operators when automation cannot resolve them.

---

## 7. Cooldown & Deduplication

To prevent action flooding during sustained incidents:

- A **cooldown timer** is set per incident type + endpoint combination after actions execute.
- Duplicate incidents hitting the same endpoints within the cooldown window are skipped.
- Cooldowns reset when the engine restarts or when a new distinct endpoint combination is affected.

## 8. System Demonstration

Running with `--once` flag against the 24 incidents from Lab 2:

```
  Incidents processed:  9
  Total actions:        23
  Successful:           23
```

The engine correctly:
- Applied `SERVICE_DEGRADATION` policy (send_alert + restart_service + throttle_traffic) to multi-endpoint incidents.
- Applied `ERROR_STORM` policy (send_alert + throttle_traffic) to single-endpoint error storms.
- Enforced cooldowns for duplicate incidents on the same endpoint combinations (15 incidents skipped due to cooldown).
- Logged all 23 response records to `storage/aiops/responses.json`.
